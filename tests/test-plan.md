## Single-session rollback-based regression script

Run `psql -X -v ON_ERROR_STOP=1 -h localhost -p 5432 -U postgres -d <confirmed-isolated-db> -f tests/financial-integrity.sql` after applying the schema and workflow scripts. It creates only synthetic fixtures and ends with `ROLLBACK`. This script covers single-session behavior: campaign gating, currency, allocation, partial and exact pledge fulfillment, refund references and limits, multi-scope refund allocation, refund rollback residue, payment references and state transitions, audit generation, and append-only history. It cannot prove inter-session locking behavior.

## Two-session concurrency tests

Run each case in its own uniquely named disposable database, absent immediately before creation, with schema and workflows installed. Use two independent `psql` sessions and coordinate the indicated steps manually. Do not run the rollback-based script concurrently with these cases; each concurrency case requires committed transactions to establish the lock outcome. Preserve exact-name creation, session, final-state, and cleanup evidence in `docs/database-execution-report.md`. Drop a test database only after confirming it was created by the current run, its owner, and zero active sessions; then verify exact-name absence. Never reuse or drop a pre-existing database.

### Competing pledge clears

1. Create an active approved campaign and a pledge for 100 INR. Create two pending donations linked to that pledge, for 60 INR each.
2. In session A, begin a transaction, set `app.actor_id`, and call `clear_donation` for donation A, but pause before commit.
3. In session B, begin a transaction, set `app.actor_id`, and call `clear_donation` for donation B. The current trigger first locks the campaign row before it locks the pledge, so B is expected to wait on A's campaign-row lock; record the actual blocker and wait event if observable.
4. Commit session A. Session B should then resume and fail with `P0001` because the newly committed 60 INR plus its 60 INR would exceed the pledge.
5. Commit or roll back session B after capturing the error. Verify the committed state: donation A is cleared with its matching ledger/audit entries; donation B remains pending with no clearing ledger/audit entry; pledge status is `PARTIALLY_FULFILLED` and net fulfillment is 60 INR.

### Competing disbursements

1. Create an active approved campaign, verified beneficiary, and exactly 100 INR of cleared funds in one restriction scope. Create and approve two disbursements in that same scope for 60 INR each.
2. In session A, begin a transaction, set `app.actor_id`, and call `pay_disbursement` for disbursement A, but pause before commit.
3. In session B, begin a transaction, set `app.actor_id`, and call `pay_disbursement` for disbursement B. It should block on the campaign row held by A.
4. Commit session A. Session B should then resume and fail with `P0001` because only 40 INR remains in the scope.
5. Commit or roll back session B after capturing the error. Verify the committed state: exactly one disbursement is paid; its single negative ledger entry and `DISBURSEMENT_PAID` audit event exist; the other disbursement remains pending without a ledger entry or paid audit event; net scope balance is 40 INR and is not negative.
